# PLAN-22 — Decouple content serializers: editor route keeps field_id keys, public API keeps label keys

## Goal

The client consumes entries exclusively through the editor routes — `GET /api/schemas/:name/entries`, `POST /api/schemas/:name/entries`, `PATCH /api/entries/:id` — and treats `values` as keyed by numeric `field_id` everywhere (`deriveInitialValues`, `entryLabel`, `DynamicEntryForm`). PLAN-21 changed the single shared `toEntry()` serializer to key `values` by field label and enrich schema-ref values to `{id, schema}`, which leaked the new shape into the editor routes the client actually uses, breaking every client read.

This plan splits the serialization: the **editor path** (`create`, `update`, `listForSchema`) reverts to the pre-PLAN-21 shape — `values` keyed by `String(field_id)` with schema-ref values as raw target-content-id numbers — while the **public path** (`listPublic`, `getPublic`) keeps the PLAN-21 label-keyed, enriched shape. The client requires no changes.

This plan depends on PLAN-21 (which introduced the label-keyed public serialization). The public API contract from PLAN-21 is preserved exactly; only the editor-path serialization is reverted to field_id keys.

## Files involved

- `server/src/services/contentService.ts` — the `toEntry()` serializer and its callers
- `server/test/contentService.test.ts` — update editor-path value assertions
- `server/test/publicApi.test.ts` — update editor-route create/update response assertions
- `SPEC.md` — revise editor-route `values` shape description, R15, and the changelog

## Implementation approach

1. **Split the serializer.** Refactor `toEntry()` so the caller chooses the value-keying scheme. The editor callers — `create()`, `update()`, `listForSchema()` — must serialize `values` keyed by `String(row.field_id)` and emit schema-ref values as the raw parsed target id number (no `{id, schema}` enrichment). The public callers — `listPublic()`, `getPublic()` — must keep the current label-keyed keys and `{id, schema}` schema-ref enrichment. Keep the `conflict` flag behavior exactly as it is today: `listForSchema` sets it, everything else omits it. Prefer a single serializer with a shape parameter over two near-duplicate methods, but either is acceptable — the behavior is what matters. Keep the `SchemaRefValue` type and the `ContentValue` union; the editor path simply won't produce `SchemaRefValue` instances.
2. **Align SPEC.md with the two shapes.** Revise the "Content (editor)" bullet in §4 so the editor `GET /api/schemas/:name/entries` response (and the editor create/update responses) are documented as keyed by `field_id` with raw schema-ref numbers, explicitly distinct from the public API's label-keyed shape. Update R15 so the label-keyed read-side claim is scoped to the public content API only (editor responses remain field_id-keyed). Revise the changelog entry to state that label-keyed `values` applies to the public content API, and that the editor entries route keeps field_id keys. The §4 value-serialization and §7 example lines apply to the public API and can stay as-is.
3. **Update tests.** In `contentService.test.ts`, the service-level serialization assertions in the "serialization (§7 example)", "coercion on save (R17)", and "conflict tracking" describe blocks exercise `create()`/`update()`/`listForSchema()` — those must assert the field_id-keyed editor shape (e.g. `values["<fieldId>"]`, raw schema-ref number), while the `listPublic`/`getPublic` assertions keep the label-keyed shape. Note two traps: the "serialization (§7 example)" test asserts `entry.values` (from `create()`, now field_id-keyed) against SPEC §7, which is a *public-route* example — the test title and assertion need to be reconciled so it no longer claims to match the §7 label-keyed example on the create() result (either assert the field_id-keyed editor shape explicitly or move the label-keyed §7 check onto a `listPublic`/`getPublic` result). And the existing equality `contentService.listPublic("car")[0].values` toEqual `entry.values` will necessarily break once `entry.values` becomes field_id-keyed — split that into two independent assertions: `listPublic` result label-keyed, `create`/`listForSchema` result field_id-keyed. In `publicApi.test.ts`, **every** assertion that reads `values` off an editor-route response — including the "editor content CRUD" block (`created.body.values`, `patched.body.values`) **and** the R19 schema-ref enrichment test's `created.body.values.owner` (whose `created` comes from `POST /api/schemas/car/entries`, an editor route) — must be reverted to the field_id-keyed shape with raw schema-ref numbers. Only assertions on the true public responses — `GET /api/content/:schema` and `GET /api/content/:schema/:id` (R18/R19/R20) — stay label-keyed. Add an assertion pinning the editor list route (`GET /api/schemas/:name/entries`) `values` shape as field_id-keyed — no test currently pins it, and this is the route the client most depends on.
4. **Verify no client changes are needed.** Confirm the client's existing field_id-keyed consumers (`client/src/lib/entries.ts` `deriveInitialValues`/`entryLabel`, `client/src/components/DynamicEntryForm.tsx` `storedValues`, `client/src/components/ReferenceSelect.tsx` raw-number handling) line up with the reverted editor shape. No client files should be modified by this plan.

## Edge cases

- **`create`/`update` responses are editor-path.** They return `ContentEntry` (no conflict flag) but are mounted on the editor routes, so they must serialize field_id-keyed like `listForSchema`. The client discards these response bodies (`useEntries.ts` handlers use `_data`), so this is safe and keeps the editor namespace consistent. **This also means existing tests that read `values` off editor-route responses — including the R19 schema-ref enrichment test's `created.body.values.owner`, where `created` is a `POST /api/schemas/car/entries` response — must be reverted to field_id-keyed, even though the R19 block otherwise tests the public API.**
- **Schema-ref value shape mismatch on the editor path.** A schema-ref field's stored value is a raw JSON number; the editor path must emit that number directly (no enrichment), which is exactly what the pre-PLAN-21 serializer did and what `ReferenceSelect`/`isValueValidForField` expect.
- **Orphaned content rows.** A `content_rows` row whose `field_id` has no matching field must be skipped (as both serializers currently do) — keep that guard on both paths.
- **Conflicted entries.** `listForSchema` includes conflicted entries with a `conflict: boolean`; only the public path filters/422s them. The `conflict` behavior must not change in this refactor.
- **SPEC consistency.** After the edit, no SPEC.md section may describe the editor route as label-keyed, and no section may describe the public API as field_id-keyed. The two shapes must be scoped correctly.

1. `pnpm --filter server test` passes, and the suite as committed contains all of the following, which together prove both serialization shapes coexist correctly:
   - the editor-list assertion in `publicApi.test.ts` that `GET /api/schemas/:name/entries` returns `values` keyed by `String(<fieldId>)` (not a label key) — the route the client reads;
   - the editor create/update response assertions in `publicApi.test.ts` — including the "editor content CRUD" block and the R19 schema-ref enrichment test's `created.body.values.owner` (both read editor-route POST responses) — reverted to field_id-keyed with raw schema-ref numbers;
   - the true public-route assertions in `publicApi.test.ts` (`GET /api/content/:schema` and `GET /api/content/:schema/:id`, the R18/R19/R20 blocks) and the `listPublic`/`getPublic` assertions in `contentService.test.ts` still label-keyed with schema-ref enriched to `{id, schema}`, unchanged.
2. `client/src/lib/api.ts` and all client files are unchanged in the commit (grep the staged diff for `client/` — it must be empty).
3. **Manual verification (cannot be fully verified by tests):** with a running dev server, edit an existing entry in the UI — fields pre-fill with stored values and the list shows proper entry labels (not "Entry #N"); create and delete an entry — no errors. This confirms the client/editor round-trip works end-to-end.
